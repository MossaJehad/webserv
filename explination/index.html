01 • Fundamentals

What is webserv?

webserv is an HTTP/1.1 compliant web server written from scratch in C++98 as part of the rigorous 42 School curriculum. The objective of this project is to demystify how real-world industrial servers like NGINX, Apache, and Envoy function beneath the surface.

Core Engineering Constraints:
  • ✓ No external libraries: No Boost, libevent, libuv, or modern C++11/17/20 STL features.
  • ✓ Single-threaded: Zero POSIX threads (pthread_create is forbidden).
  • ✓ Single poll() reactor: One central event loop drives all listening sockets, client streams, and CGI pipes simultaneously.
  • ✓ Non-blocking I/O: Every descriptor must use O_NONBLOCK. Never block the event loop on slow clients or network latency.
02 • Architectural Rationale

The C10K Challenge & The Reactor Pattern

In early web servers (like the original Apache prefork model), each incoming client connection was dispatched to a separate thread or spawned process. If 10,000 clients connected simultaneously, the operating system kernel wasted excessive CPU time switching thread contexts, allocating massive stack memory per thread, and exhausting descriptor tables. This is famously known as the C10K problem.

Thread-Per-Client (Anti-pattern for webserv)

A thread blocks on read() until the client sends data. If a malicious client sends 1 byte every 10 seconds (Slowloris attack), the thread remains frozen, consuming stack memory and blocking server capacity.

Single-Loop Non-Blocking Reactor (webserv)

The server sets all sockets to non-blocking with fcntl(). A single call to poll() sleeps until the operating system notifies that at least one file descriptor is ready for reading or writing. No threads, no context switching overhead, virtually zero idle CPU usage.

03 • System Decomposition

Layered Modular Architecture & Frozen Contracts

Many 42 students fail webserv because they write a monolithic 3,000-line socket loop where HTTP parsing, CGI execution, and socket reading are tangled together in nested conditions. In this codebase, strict separation of concerns and unidirectional dependencies are enforced:

1. Core Layer (src/core/) Bootstrapping & Signals

Contains Webserv and Signal. Parses the configuration file, sets up signal handlers (SIGINT, SIGTERM, SIGPIPE ignored), instantiates listeners, and starts the reactor.

2. Network Layer (src/net/) Sockets & Event Dispatch

Reactor, PollRegistry, Listener, and Socket. Has zero knowledge of HTTP. It only knows about file descriptors, readiness flags (POLLIN, POLLOUT), and the polymorphic IEventHandler interface.

3. Connection Layer (src/connection/) Client State Machine

Connection and ConnectionManager. Implements IEventHandler. Manages the lifecycle of a client socket: buffering inbound and outbound bytes, advancing states, detecting timeouts, and managing lingering close.

4. HTTP & Routing Layer (src/http/ & src/routing/) Parsing & VHost Matching

RequestParser, ChunkedDecoder, Router, and ResponseSerializer. Pure data manipulation without touching socket file descriptors! Makes the parsing engine 100% testable via unit tests.

5. Handlers & CGI Layer (src/handlers/ & src/cgi/) Response Generation

StaticFileHandler, UploadHandler, DeleteHandler, AutoindexHandler, and CgiProcess. Generates responses based on the request method and URI.

04 • Event Dispatching

The poll() Reactor Event Loop Explained

The heart of webserv is Reactor::run() in src/net/Reactor.cpp. Here is how the loop executes every 100 milliseconds:

Core Loop snippet from src/net/Reactor.cpp 
void Reactor::run() {
    _running = true;
    std::vector<struct pollfd> pollfds;

    while (_running && !Signal::isStopping()) {
        // 1. Collect pollfds from all registered handlers (listeners, clients, pipes)
        _registry.buildPollFds(pollfds);

        struct pollfd* fds = pollfds.empty() ? NULL : &pollfds[0];

        // 2. Sleep in kernel until at least one fd is ready (or 100ms timeout)
        int ready = poll(fds, pollfds.size(), POLL_TIMEOUT_MS);

        if (ready > 0) {
            dispatch(pollfds);
        }

        // 3. Periodic sweep: disconnect clients that stalled or exceeded keep-alive
        _connManager.sweepDeadAndTimedOut(_registry);
    }
}
Critical Rule: Read & Write in the Same Loop Cycle

In Reactor::dispatch, notice how if a file descriptor has both POLLIN and POLLOUT ready, the reactor handles handleRead() first, re-verifies that the descriptor wasn't closed, and then immediately runs handleWrite() in the same iteration. This minimizes client latency by a full poll tick!

05 • State Machine

Client Connection Lifecycle & State Transitions

Each TCP client connection is modeled as a formal Finite State Machine (FSM) inside src/connection/Connection.hpp. Sockets never block on I/O. Instead, they transition between explicit states:

State wantsRead wantsWrite Description & Next Transition
CONN_STATE_READING true false Receiving bytes into IoBuffer. Feeds incremental parser. Transitions to PROCESSING once the request is complete.
CONN_STATE_PROCESSING false false Matches virtual host, executes routing, and invokes handler. If CGI is selected → transitions to WAIT_CGI; otherwise generates response → transitions to WRITING.
CONN_STATE_WAIT_CGI true (drain) false Asynchronous child script is executing. The client socket remains monitored for disconnects or pipelined requests (drainWhileBusy). Once CGI finishes → transitions to WRITING.
CONN_STATE_WRITING false true Flushing serialized response buffer via send(). Once buffer is empty: if keep-alive → resets to READING; if rejected upload → LINGER; otherwise CLOSED.
CONN_STATE_LINGER true false Draining remaining unread upload body before closing socket. Prevents TCP reset (ECONNRESET) from destroying the error response in client browser.
CONN_STATE_CLOSED false false Socket is closed via RAII destructor, unregistered from poll, and deallocated by ConnectionManager.
06 • Protocol Parsing

HTTP/1.1 Incremental Streaming Parser

In non-blocking networking, recv() rarely returns an entire HTTP request at once. It may return 10 bytes, 1500 bytes (one MTU packet), or a fragment of a header line. The parser in src/http/RequestParser.cpp operates as an incremental stream parser:

1. Request Line Parsing

Scans for \r\n. Splits exactly into 3 parts: METHOD SP URI SP VERSION. RFC 7230 prohibits control characters (< 0x20 or 0x7F). Bounded to 8,192 bytes; exceeding this returns 414 URI Too Long.

2. Header Section Bounds

Extracts key-value pairs delimited by colons. Enforces case-insensitive matching. Bounded to 32,768 bytes total and max 100 headers to prevent memory exhaustion (returning 431 Request Header Fields Too Large). RFC 7230 5.4 mandates rejecting duplicate Host headers with 400.

3. Body with Content-Length

When Content-Length: N is present, reads exactly N bytes. If N > client_max_body_size, parsing aborts immediately with 413 Payload Too Large before allocating body memory!

4. Leftover Preservation

In HTTP/1.1 pipelining, a client may send the start of a second request within the same TCP packet. The parser saves leftovers via takeLeftover() and restores them when the next request is processed.

07 • RFC 7230 Chunked Decoding

Chunked Transfer Encoding (Transfer-Encoding: chunked)

Chunked transfer encoding allows a client to stream dynamic data of unknown total size. The payload is sent in consecutive chunks, where each chunk begins with its size in hexadecimal, followed by \r\n, the chunk data, and another \r\n. The stream terminates with a zero-length chunk 0\r\n\r\n.

RFC 7230 Chunked Body Structure src/http/ChunkedDecoder.cpp 
4\r\n        <-- Hexadecimal chunk size (4 bytes)
Wiki\r\n    <-- 4 bytes of data + CRLF
6\r\n        <-- Hexadecimal chunk size (6 bytes)
pedia \r\n  <-- 6 bytes of data + CRLF
E\r\n        <-- Hexadecimal chunk size (14 bytes in hex: 'E')
 in \r\n\r\nchunks.\r\n
0\r\n        <-- Terminal chunk size 0
\r\n        <-- Final CRLF delimiter (or trailers)
Request Smuggling Defense

In ChunkedDecoder::feed, we enforce strict \r\n between chunks. If a client sends a bare \n without \r, it is rejected immediately. Accepting loose line endings allows attackers to desynchronize reverse proxies and cache servers (HTTP Request Smuggling)!

08 • Request Dispatching

Virtual Hosts, Longest Prefix Routing & Handlers

Once a request is parsed into an HttpRequest, the Router maps it to a specific virtual server and location:

1. Virtual Host Matching (Server Block)

The router first filters servers listening on the exact connected TCP port. It then matches the client's Host: example.com header against the configured server_name directives. If no server_name matches, it falls back to the default virtual host (the first server defined on that port).

2. Longest Prefix Location Match

If the server configuration has location / and location /uploads, a request to /uploads/file.png will match /uploads because it is the longest prefix match on path boundaries.

3. Handler Factory Pattern

Decoupled polymorphic handlers inherit from IRequestHandler:

StaticFileHandler
Serves static assets with MIME types, checks directory index (index.html), or generates directory autoindex.
UploadHandler
Parses multipart/form-data and raw uploads, sanitizes filenames to prevent path traversal, returns 201 Created.
DeleteHandler
Deletes files safely via unlink(). Prevents directory deletion without proper permissions. Returns 200 OK or 204 No Content.
RedirectHandler
Handles return 301 / or return 302 http://... with an automatic Location header.
09 • RFC 3875 Common Gateway Interface

Asynchronous Non-Blocking CGI Pipeline

Executing external scripts (Python, Bash, PHP) is the most challenging requirement of webserv. A naive fork() + blocking waitpid() freezes the entire web server, meaning all other connected users cannot even load static pages!

How webserv executes CGI without blocking:
Webserv Reactor Loop (Single Process)
    |
    |-- 1. pipe(inPipe) & pipe(outPipe)
    |-- 2. fcntl(..., O_NONBLOCK) on parent pipe ends
    |-- 3. fork() child process
    |       |-- Child: dup2() inPipe[0] -> STDIN
    |       |-- Child: dup2() outPipe[1] -> STDOUT
    |       |-- Child: close all inherited server fds (FD_CLOEXEC)
    |       |-- Child: chdir to script directory
    |       |-- Child: execve(interpreter, argv, envp)
    |
    |-- 4. Parent registers inPipe[1] (writeHandler) & outPipe[0] (readHandler) in PollRegistry
    |-- 5. Connection enters CONN_STATE_WAIT_CGI
    |
Reactor poll() notifications:
    |-- outPipe[0] is POLLIN  --> CgiProcess::handleStdoutRead() (accumulates script output)
    |-- inPipe[1]  is POLLOUT --> CgiProcess::handleStdinWrite() (streams POST request body)
    |-- Child closes stdout   --> CgiResponseParser parses headers + body --> response sent
    |-- Script exceeds 10s    --> kill(pid, SIGKILL) + waitpid() --> sends 504 Gateway Timeout
Zero Zombie Procs

In CgiProcess::reapChild, every child is reaped via non-blocking waitpid(_pid, &status, WNOHANG). If still running upon timeout, it is killed with SIGKILL and harvested immediately.

FD_CLOEXEC Hygiene

All listening sockets and parent pipes have FD_CLOEXEC set. If a CGI script runs indefinitely, it will never prevent webserv from binding or unbinding its listening ports.

Body Un-chunking

CGI scripts (like Python) expect clean input with an accurate CONTENT_LENGTH. The server decodes chunked bodies first, feeding raw bytes directly so scripts see EOF at the end.

10 • Reliability Engineering

Defensive Design: Slowloris, Timeouts & Lingering Close

During 42 evaluations, evaluators will deliberately send malformed requests, open idle connections, cut internet cables, and upload massive files to test if your server crashes, leaks memory, or freezes. Here is how our server handles these scenarios:

1. Slowloris Defense (Dual Timeouts) 60s Idle / 20s In-Flight

An idle keep-alive socket waiting for a new request has a generous 60-second timeout. However, if a client starts sending a request line or headers but stalls mid-transmission, the connection enters a strict 20-second in-flight timeout. If the client fails to complete the request within 20 seconds, the server sends a 408 Request Timeout and closes the socket!

2. Lingering Close (Rejected Uploads) CONN_STATE_LINGER

When a client attempts to upload a 50MB file to a route that allows only 1MB, the server immediately sends 413 Payload Too Large. If the server closes the TCP connection immediately while the client is still pushing data, the kernel will send a TCP RST packet. The client's browser will see "Connection Reset" and discard the 413 error page! To prevent this, our server transitions to CONN_STATE_LINGER, reading and discarding incoming data until the client finishes or a 5-second linger timeout expires.

3. Out-Of-Memory (OOM) Protection std::bad_alloc Trap

In src/main.cpp and src/net/Reactor.cpp, top-level try / catch blocks trap memory allocation failures. If an excessively large payload causes std::bad_alloc, only that offending client connection is dropped. The server itself never crashes and continues accepting other clients!

11 • Source Code Tour

Interactive Codebase Directory & Class Catalog

Browse through each source module in the project to inspect file responsibilities, design patterns, and exact line counts:

src/core/ Bootstrap & Lifecycle
  • Webserv (.hpp/.cpp): Central coordinator. Parses configuration, groups server blocks by unique (host, port) pairs, instantiates Listener objects, and starts the Reactor.
  • Signal (.hpp/.cpp): Installs global signal handlers using sigaction(). Flags atomic shutdown on SIGINT and ignores SIGPIPE so broken client sockets never crash the server.
src/net/ I/O Multiplexing & Event Loop
  • Reactor (.hpp/.cpp): The central poll() event loop. Builds the pollfd vector, calls poll() with a 100ms timeout, and dispatches readiness to registered handlers.
  • PollRegistry (.hpp/.cpp): Bidirectional mapping between integer file descriptors and IEventHandler*. Guards against stale descriptor re-registration.
  • Listener (.hpp/.cpp): Wraps a server listening socket. Resolves IPv4 hostnames via getaddrinfo(), calls bind() and listen(), and on POLLIN runs accept() to create new connections.
  • Socket (.hpp/.cpp): RAII socket descriptor wrapper. Provides helper functions: setNonBlocking(), setReuseAddr(), and setCloexec().
src/connection/ Per-Client State & Buffers
  • Connection (.hpp/.cpp): The client state machine. Owns input/output buffers, parses incoming requests, triggers routing and handlers, and flushes output bytes non-blockingly.
  • ConnectionManager (.hpp/.cpp): Registry of active client connections. Periodically sweeps for dead or timed-out connections.
  • IoBuffer (.hpp/.cpp): Efficient FIFO byte buffer for streaming read/write operations without reallocation overhead.
src/http/ RFC 7230/7231 Parser & Formatter
  • RequestParser (.hpp/.cpp): Multi-stage incremental stream parser for request lines, HTTP headers, and Content-Length bodies.
  • ChunkedDecoder (.hpp/.cpp): RFC 7230 chunked transfer decoder with strict CRLF checks and chunk size bounds.
  • ResponseSerializer (.hpp/.cpp): Formats HttpResponse objects into compliant HTTP/1.1 wire protocol byte streams.
src/routing/ & src/handlers/ Routing & Actions
  • Router (.hpp/.cpp): Matches Host header to virtual server, resolves longest matching location block, and checks allowed HTTP methods.
  • StaticFileHandler: Serves files, detects MIME types, serves index files or directory autoindexes.
  • UploadHandler & DeleteHandler: Handles multipart form uploads and file deletions via unlink().
src/cgi/ RFC 3875 Script IPC
  • CgiProcess (.hpp/.cpp): Forks child, sets up bidirectional non-blocking pipes, registers pipe handlers in the reactor, monitors execution timeout, and reaps child processes.
  • CgiEnvironment (.hpp/.cpp): Populates standard RFC 3875 environment variables (REQUEST_METHOD, QUERY_STRING, CONTENT_LENGTH, SCRIPT_NAME, etc.).
  • CgiResponseParser (.hpp/.cpp): Separates CGI output headers (Status:, Content-Type:) from the generated response body.
12 • Evaluation Defense Guide

42 Evaluation Masterclass: Defend Your Project With Confidence

During your peer evaluation, the evaluators are instructed to grill you on your design decisions, poll usage, descriptor handling, and RFC edge cases. Below are the exact questions they will ask and how to answer them like a senior systems engineer:

Q1: "Why only one poll() loop? Can you show me in code where poll() is called?" ↓

Answer: The subject strictly mandates that all I/O operations (listening sockets, client TCP streams, and CGI pipes) must be multiplexed through a single central poll() (or select/kqueue/epoll).

Open src/net/Reactor.cpp at line 41. Point directly to: 

int ready = poll(fds, pollfds.size(), POLL_TIMEOUT_MS);

Explain that every file descriptor in the process lives inside PollRegistry. We never call poll() in any secondary function, thread, or CGI handler.

Q2: "How do you guarantee that a client socket never blocks the server?" ↓

Answer: Every socket accepted by accept() has fcntl(fd, F_SETFL, O_NONBLOCK) called on it immediately inside Connection::Connection (via Socket::setNonBlocking).

Furthermore, recv() and send() are only ever invoked when the Reactor confirms that poll() returned POLLIN or POLLOUT for that exact descriptor. If a client stalls, poll() simply does not flag it, allowing other clients to be served without interruption.

Q3: "What prevents CGI scripts from blocking the server or leaking zombie processes?" ↓

Answer: Three complementary safeguards in src/cgi/CgiProcess.cpp:

  1. Non-blocking Pipes: Parent pipe ends are set to non-blocking and registered directly into the central PollRegistry. The server feeds stdin and reads stdout asynchronously via the main reactor loop.
  2. Process Reaping: The parent never runs blocking wait(). It uses waitpid(_pid, &status, WNOHANG). If the child hasn't terminated, the reactor continues running.
  3. Timeout & Kill: If a script exceeds 10 seconds (e.g. an infinite loop), checkTimeout() triggers kill(_pid, SIGKILL) and returns 504 Gateway Timeout.
Q4: "Why do you use FD_CLOEXEC on your sockets?" ↓

Answer: When webserv calls fork() to execute a CGI script, by default all open file descriptors in the parent process are duplicated in the child process.

If a CGI script inherits our listening socket (e.g. port 8080) and runs for 10 minutes, and the server is restarted during that time, the kernel will return EADDRINUSE (Address already in use) because the child script is still holding the socket open! Setting FD_CLOEXEC ensures the operating system automatically closes all listening and client sockets upon execve().

Q5: "How do you test for memory leaks and descriptor leaks?" ↓

Demonstrate the built-in commands from our README: 

# Run with Valgrind leak and descriptor tracking
valgrind --leak-check=full --track-fds=yes ./webserv config/default.conf

# In another terminal, run the full integration and siege stress suite:
python3 tests/integration/test_regression.py --all
siege -b -c 25 -t 30S http://127.0.0.1:8080/

Show the evaluator that open descriptor count remains strictly constant and Valgrind reports zero leaks.
